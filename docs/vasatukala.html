How Pun builds and runs a page

Two flows, drawn from the PUN 4.0.0 source code. Build turns .pun templates into one .pind bundle. Runtime loads that bundle once when Pun Server starts, then runs a page for every request.

Words to know

.pun source template

The page you write: ordinary HTML with <?pun … ?> blocks. Pun Server can run it straight from the folder, or build can compile it.

.ghar compiled page · ਘਰ, home

One page inside a bundle. Version 1 holds the page's syntax tree (AST) for the interpreter. Version 2 holds PUN VM instructions. Both keep the literal HTML as text.

.pind application bundle · ਪਿੰਡ, village

The whole app in one compressed ZIP file: every .ghar page, the public assets, the route controller and a manifest. You deploy just this file.

.raah.json route controller · ਰਾਹ, way

Which URL runs which page. It lives in your source folder, and build copies it into the .pind.

PUN VM ≠ JVM two different engines

The PUN VM is Pun's own instruction engine: a loop inside Pun Server that runs version 2 instructions. The JVM (Java Virtual Machine) runs Pun Server itself. Pun can turn PUN VM instructions into JVM classes so the JVM runs them directly.

AST interpreter the original engine

Walks the syntax tree statement by statement. It runs .pun source pages and version 1 .ghar pages.

Timing

When each step happens

  1. Build time The page format is chosen

    build (or Build PIND in the desktop app) compiles every page, picks its .ghar version and packs everything into one .pind. Once per build, on your machine.

  2. Server startup JVM code is prepared

    Pun Server finds and checks each bundle, verifies its version 2 pages and turns them into JVM classes in memory. Once per server start.

  3. Every request The page runs

    The URL picks a page, new mang, jawab and variables are made, and the page runs on the interpreter, the PUN VM or as JVM code.

Kept and reused

Decoded pages, verified PUN VM instructions, generated JVM classes, routes and assets stay in memory for as long as the server runs. Parsed .pun source pages are cached too. Restart the server to load a rebuilt bundle.

New for every request

mang, jawab, every variable, every kaam value and the output buffer. Nothing a page sets carries over to the next request.

The JVM tier in detail

-Dpun.vm.jvm=false

A JVM option, placed before -jar:

java -Dpun.vm.jvm=false -jar target/pun-server.jar serve chowk

Pun Server then makes no JVM classes, and every unit of every version 2 page runs on the PUN VM. The bundle and the page output stay the same; only speed changes. Version 1 and source pages aren't affected. Only the value false, in any letter case, turns the tier off. Given to build, it makes the dry run report JVM code: 0 of N units.

The 8,000-byte limit

Pun translates one unit at a time: each kaam and each <?pun … ?> block. While it writes a unit's JVM method it counts the method's bytecode. Past 8,000 bytes it gives up on that unit, which stays on the PUN VM; exactly 8,000 is still translated. The limit is per unit, not per page or bundle, and it counts JVM bytecode, not Pun source lines or VM instructions.

8,000 is HotSpot's HugeMethodLimit: by default HotSpot never compiles a larger method to machine code. A unit also stays on the VM if its method would need more than 65,535 local variables or it has more than 250 parameters.

When translation fails

If translating a page throws an error, or the JVM refuses to define, verify or initialise the generated class, every unit of that page stays on the PUN VM, which runs the same instructions with the same output. Pun prints one warning to stderr, only for the first such page in a server run, and the startup log lists the page under on the VM. Other pages keep their JVM code.

Where the classes live

One class per version 2 page, written as bytes in memory and defined by its own class loader while the bundle loads. Nothing is added to the .pind or written to disk, and the classes are made again on every start. For debugging, -Dpun.vm.jvm.dump=<folder> writes a copy of each class there, to read with javap -c -p.

Each HTTP requestRuns every time, with fresh state

Static asset or dynamic page?

A path in the route map runs a page. Any other path is looked up among the bundle's assets and sent straight from memory, typed by its extension; no Pun code runs. Anything else is a 404: a mounted app never falls through to files on disk.

JVM code and the PUN VM, together

Each unit runs where startup put it. When JVM code calls a kaam that stayed on the PUN VM, that kaam runs on the VM loop; when VM code calls a translated kaam, it enters the JVM method. Both use the same request's variables, so the output matches an all-VM run.

HotSpot JIT is separate

HotSpot is the JVM's own just-in-time compiler. It watches all running Java code, including the generated page classes, the PUN VM loop and the interpreter, and compiles hot methods to machine code. That's why new JVM code starts slow and speeds up over the first few hundred requests. HotSpot never decides whether a unit runs as JVM code or on the PUN VM; Pun settles that when the bundle loads.

See which engine ran

Start the server with -Dpun.engine.header=true and each Pun response carries X-Pun-Engine: jvm, vm, jvm+vm (n units on the VM) or interpreter. It's meant for benchmarks; leave it off in production.

Without a build

Source .pun pages

Always the interpreter

Plain .pun pages, served from the folder without a build, keep the original path: template scan, lexer, parser and AST interpreter. They never use the PUN VM or JVM code.

Pun Server keeps the parsed AST of unchanged files up to 128 KiB (128 files and 16 MiB in all), so repeat requests skip the lexer and parser. Edit a file and the next request parses it again. The limits are set with the -Dpun.cache.* options.

Security

Bundles and protected files

Bundling is not encryption

A .pind is an ordinary ZIP file. Anyone with a copy can unzip it and read the HTML, names and text values in its pages, including a database password written in a .pun file. Version 1 pages hold the serialized syntax tree and version 2 pages the VM instructions; neither is protected. Treat a bundle like its source.

What Pun Server blocks

Pun Server answers 404 to any URL with a path segment named META-INF, or ending in .pind, .ghar or .raah.json, in any letter case. It checks before routing, for compiled apps and source folders alike.

That only covers requests Pun Server handles. If a separate web server or reverse proxy serves the folder itself, configure it to refuse those files, or keep them out of its public folder.

Every other file becomes public

build packs every file in the source folder that isn't a .pun page as a public asset, dotfiles included. A .env inside the folder ends up in the bundle, and the mounted app serves it, for example at /shop_pind/.env. Keep secrets outside the folder you build.
